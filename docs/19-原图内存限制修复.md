# 原图加载 Memory limit exceeded 修复

## 用户确认的行为

打开详情必须继续加载原图，不改成只显示缩略图，不做 2000px 降采样，也不再由应用的固定内存/尺寸配额拒绝有效原图。此前关于“取消自动原图预览”的提议是误解，没有实施。

本轮只修改原图预览路径；缩略图加载、头像和手动下载已有行为保持不变。

## 原因与修复

旧 `ImageLoader::preview` 下载原图后调用与缩略图共享的 `decode(bytes, 2000)`：

1. 原图 HTTP 响应限制为 128 MiB。
2. 解码器设置 `max_alloc=256 MiB`、宽高各不超过 20000px。
3. 完整解码成功后才缩小为最长边 2000px。

压缩文件小不代表解码内存小。合成的 12000×8000 JPEG 压缩后约 550 KiB，但 RGB 解码需要 288,000,000 字节，直接触发旧配额；同一个实际 HTTP 预览入口测试在修复前精确返回 `Memory limit exceeded`。

现在原图路径独立处理：读取完整响应、`ImageReader::no_limits()`、解码为原生分辨率 RGBA；不再调用缩略图的受限解码及缩放函数。旧的 128 MiB 原图响应限制、256 MiB 配额、20000px 边长上限和 2000px 缩小均不再适用于原图预览。主详情与上传者主页共用此入口。

详情加载完成后显示“原图已加载 · 宽 × 高”，主页显示相同实际尺寸，避免把仍在显示的缓存缩略图误认为原图已经完成。

HTTP 状态检查、网络超时和解码错误仍正常处理。这里移除的是应用人为大小/解码配额，不意味着系统资源无限：真实内存不足、图片损坏、解码器格式限制、GPU/渲染能力或网络错误仍可能失败。

## 回归与检查

新增 3 个实际 `ImageLoader::preview` HTTP 回归：

- **12000×8000 JPEG**：旧代码先失败 `valid original must load, not fail with: Memory limit exceeded`，修复后返回完整 12000×8000、384,000,000 字节 RGBA，未缩成 2000px。
- **20001×1 PNG / 超过 128 MiB 响应**：使用带尾随填充的合法 PNG 响应隔离旧尺寸/响应上限，返回完整尺寸和预期像素。该测试证明响应上限移除，不伪称对复杂 128 MiB PNG 的性能验收。
- **损坏图片 / HTTP 404**：仍返回错误，不将无效数据当成图片。

合成 JPEG 保存在 `rust/desktop/tests/fixtures/preview-12000x8000.jpg`，无用户内容；旁边 README 记录生成方式。大图测试会使用数百 MiB 工作内存。

执行：

```powershell
cd D:\Code\wallhaven\rust
cargo test -p wh-desktop original_preview -- --nocapture
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check

```

结果：核心 **38 通过 / 1 忽略**，桌面 **87 通过 / 3 忽略**，共 **125 项常规测试通过**，无失败。Clippy、格式、Release 构建通过。原有下载成功、失败清理、不覆盖文件测试继续通过；没有为测试实际下载到用户图片目录。

## 桌面观察与边界

- 新 Release 已启动，详情 `e882e8` 实际显示“原图已加载 · 4751 × 8444”，已确认不再缩成最长边 2000px；应用保持响应。
- 公开查询确认 `mlzdom` 为 SFW PNG、15360×10240、约 1.2 MB，适合验证旧配额问题；本轮没有完成它的最终原生显示验收，不能将 API 尺寸查询当成已显示。
- 主窗口在验收期间发生切换，为避免干扰用户操作停止继续驱动它。隔离验收启动器被桌面工具的路径保护拒绝，未绕过，也未计作通过。
- 本轮未改真实配置：仍为 38 字节，修改时间 2026-10-18 12:22:46 UTC；没有清除登录、保存设置或执行站内写入。
- 没有拿到用户最初报错的具体图片 ID，因此没有声称已逐图复验该原始图片。相同报错在可重复的大图样本上已经复现并修复。

本记录对原图预览限制的说明取代早期文档中的 2000px / 256 MiB / 20000px 原图限制描述；缩略图与手动下载限制未在本轮修改。
