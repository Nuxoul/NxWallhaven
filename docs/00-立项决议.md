# WallHaven Desktop/Mobile — 立项决议

> 状态：**待你签字确认（Go/No-Go）**
> 版本：v0.1（方案稿）
> 日期：2026-10-19
> 依据：`docs/01-调研报告.md` 中的实测与官方文档核验

---

## 1. 一句话定义

把 wallhaven.cc 网页端的检索、浏览、收藏、下载能力，重构为 **Windows 桌面端 + Android 移动端** 的原生体验应用，并叠加网页端没有的**本地数据管线**：元数据入库、标签清洗与去重、本地图库、智能下载与壁纸轮换。

**项目代号（建议）**：`WallHaven Studio`（下文简称 WHS）
**边界**：第三方客户端，**不抓取/不代理 HTML 页面，只走官方 API v1**；不内嵌站点凭据，不绕过 NSFW 门禁。

## 2. 技术选型结论（核心）

### 结论：**Kotlin + Compose Multiplatform** 单代码库，覆盖 Windows 与 Android；**Rust 作为可选加速模块（Phase 3 才引入）**。

**明确否决**：
- **纯 Go（Wails / Fyne / Gio）** — 理由见 §2.3
- **纯 Rust（Tauri v2 / Dioxus / Slint）** — 可作为备选，但在本项目两项目标平台上处于结构劣势
- **Flutter** — 可行，但与本仓库的 Kotlin/Gradle 生态割裂，且桌面端仍需平台插件
- **Electron** — 包体 100MB+、内存占用高，与"桌面壁纸工具"常驻场景冲突

### 2.1 决策矩阵（权重按本项目真实诉求）

| 维度 | 权重 | Kotlin/CMP | Rust/Tauri v2 | Go/Wails | Go/Fyne | C#/Avalonia |
|---|---|---|---|---|---|---|
| Android 支持成熟度 | 25% | **5** 一等公民 | 3 需 Studio+jni 链路 | **1** 官方不支持 | 2 实验性 | 2 社区绑定 |
| 同一 UI 代码两端复用 | 20% | **5** | 4 | 2 | 4 | 3 |
| 大量图片列表性能 | 15% | **5** LazyGrid+Coil | 4 | 3 | 2 易卡顿 | 4 |
| 桌面系统集成（壁纸/托盘） | 10% | 3 需少量 JNI | **5** Rust 原生 | 4 | 4 | **5** WinRT |
| 包体/内存 | 10% | 3（Android ~12MB；桌面**实测 114MB**，含裁剪 JRE 64.7MB） | **5**（~10MB） | 4 | 4 | 2 |
| 后台任务/数据库生态 | 10% | **5** Room/SQLDelight/WorkManager | 4 | 3 | 3 | 4 |
| 本机环境就绪度 | 10% | **5** JDK17+SDK37 已在位 | 4 缺 Android target | 1 无 Go | 1 无 Go | 4 |
> **2026-10-19 复核更新**：本矩阵对 Rust/Slint/Tauri 的评分基于"单套原生 UI"这一前提。若你接受**两端各自独立 UI**，方案 D（桌面 Tauri + 安卓 Kotlin + Rust 共享核心）也是优解，见 `03-选型复核-Rust方案分析.md`。

> **桌面端可行性已实测闭环**：本次真实建工程 → `compileKotlin` SUCCESSFUL → `createDistributable` 产出 `kt-desktop-proof.exe` → **枚举到真实窗口标题 "WH Studio - Compose Desktop Proof"**，包内含 `skiko-windows-x64.dll`（14.1MB，Skia 原生渲染）。详见 `01-调研报告.md` §2.3。**Kotlin 不是只能写安卓。**

> **唯一实质短板：体积**。桌面分发包实测 **114.4MB**（JRE 64.7MB + 应用 49.7MB），Tauri 同类约 8–15MB。若你对安装包大小极其敏感，这是唯一值得为此改选 Tauri 的理由。

加权得分：**Kotlin/CMP ≈ 4.55** ＞ Rust/Tauri ≈ 4.05 ＞ Avalonia ≈ 3.25 ＞ Fyne ≈ 2.75 ＞ Wails ≈ 1.95

### 2.2 为什么是 Kotlin + Compose Multiplatform

1. **Android 是原生主场**：SharedPreferences/WorkManager/Room/Coil 全是一等支持；壁纸设置用 `WallpaperManager` 或 MediaStore 都是一行调用。
2. **Windows 端不再"二等公民"**：CMP 的 Windows 目标已稳定（Compose 1.12.x），可产出 MSI；窗口、托盘、文件对话框都有现成 binding。
3. **业务域天然适合 KMP**：本项目 80% 复杂度在 `shared` 层（API 客户端、清洗管线、SQLite、调度），UI 只占 20%——正是 KMP 收益最大的结构。
4. **图片性能**：Coil 3 是 Kotlin Multiplatform 原生项目，`coil-compose` 在 Android 用 Skia、在桌面用 Skiko，一套 `AsyncImage` 两端通用，且自带三级缓存与采样降档——这是本项目最吃紧的性能点。
5. **环境成本最低**：本机 Rust 只有 `x86_64-pc-windows-msvc` target，走 Tauri 安卓需额外装 NDK 配置、`cargo-ndk`、签到 Android Studio 的 Gradle 链路；Kotlin 路线当前环境基本开箱即用。

### 2.3 为什么否决 Go

- **Wails**：官方移动端支持不到位（需第三方 `wails-mobile` 分支，成熟度低）。它本质是"Go 后端 + WebView 前端"，Android 侧等于回到 WebView 套壳，性能与"原生体验"目标相悖。
- **Fyne**：跨平台最省事，但移动端渲染与手势是明显短板；海量图片瀑布流滚动会掉帧；且它是**自绘像素级 UI**，无法复用 Material 3 组件与平台约定。
- **结论**：Go 适合本项目未来的**服务端/CLI 批量抓取工具**（若需要），不适合两端口碑级 GUI。

> 若你个人强烈偏好 Go，备选路线保留：`Go 核心逻辑 → 编译为 .so/.dll → Kotlin/Flutter 前端调用`（gomobile bind + CGO）。但这会增加构建复杂度，仅在你已有大量 Go 代码资产时才有意义。

### 2.4 Rust 的正确用法（Phase 3 可选）

不用于 UI，而用于两个**确实吃 CPU**的地方：
- 批量下载时的并发调度 + 校验（`tokio` + `reqwest`）
- 图片后处理：转码/缩略图/多分辨率生成（`image` crate，比 JVM 快 3–5×）

以 `cdylib` 形式经 `jni` 或 `uniffi` 暴露给 Kotlin。**Phase 1/2 一律不做**，先用 Kotlin 协程顶住，避免过早优化。

- 冷启动 Windows < 2.5s / Android < 1.5s

## 4. 关键约束（已实测确认，写进架构红线）

| 约束 | 实测值 | 架构影响 |
|---|---|---|
| API 限流 | **45 次/分钟** | 全局令牌桶 + 请求队列，客户端单例化 |
| 分页上限 | **254 页硬上限**，page>last_page 返回空数组 | 批量抓取必须按「过滤条件切片」而非无限翻页 |
| 单页条数 | 固定 **24**，不可调 | 瀑布流按 24 为单位预取 |
| 列表不含 tags/uploader | 仅详情页 `/w/{id}` 有 | 标签清洗需额外 1 次请求/图 → 必须做**增量+缓存** |
| NSFW | 需 API Key，否则 401 | Key 可选，缺失时锁 purity=100 |
| API 性质 | 只读；官方声明"可随时无预警变更" | API 层必须**防腐隔离**（Anti-Corruption Layer），字段缺失要容错 |
| 图片直链 | `w.wallhaven.cc` 可直连，无鉴权 | 下载无需走 API 配额，可高并发（但要自限速，做良好公民） |

## 5. 架构（分层 + 防腐）

```
┌──────────────────────────────────────────────┐
│  UI 层（Compose Multiplatform，代码共享）      │
│  Screens: Search / Wallpaper / Collections /  │
│           Downloads / Library / Settings      │
├──────────────────────────────────────────────┤
│  Presentation: ViewModel (KMP) + UiState      │
├──────────────────────────────────────────────┤
│  Domain 层（纯 Kotlin，无平台依赖）            │
│  UseCase / Model / 清洗规则（可单测 100%）     │
├──────────────────────────────────────────────┤
│  Data 层                                      │
│  ├ WallhavenApi  ← ACL，字段全 optional        │
│  ├ RateLimiter（45/min 令牌桶）                │
│  ├ Repository（网络+DB 单一事实来源）          │
│  ├ SqlDelight（共享 schema，两端 SQLite）      │
│  └ ImageLoader（Coil 3）                      │
├──────────────────────────────────────────────┤
│  Platform（expect/actual）                     │
│  桌面: 壁纸设置/托盘/多显示器/文件系统         │
│  安卓: WallpaperManager/WorkManager/SAF        │
└──────────────────────────────────────────────┘
```

**铁律**：
1. `shared/domain` 与 `shared/data` 禁止 import 任何 `android.*` 或 `java.awt.*`——由 `explicitApi` + 编译期检查守护。
2. UI 状态一律不可变 `data class`，单向数据流。
3. API 返回模型与领域模型**分离**，禁止直接把 JSON 对象丢给 UI。

## 6. 数据方案（"清洗数据"的落地）

**SQLite（SqlDelight）表**：
- `wallpapers(id PK, resolution, ratio, file_size, purity, category, colors, path, ...)`
- `tags(id PK, name, alias, category, purity)` / `wallpaper_tag(wallpaper_id, tag_id)`
- `downloads(wallpaper_id, state, bytes_done, local_path, sha256)`
- `queries(id, params_json, last_page, synced_at)` — 断点续抓
- `collections` / `collection_item`

**清洗规则（可配置、可测试）**：
1. **标签归一**：小写化、去首尾空白、中文别名映射（如 `anime` ↔ `Chinese cartoons` 合并为同一 tag_id）
2. **去重**：以 `id` 为准；另以 `(resolution, file_size, sha256)` 检测重复文件
3. **补全**：缺失 `colors`/`ratio` 由 `dimension_x/y` 反算
4. **过滤**：分辨率下限、宽高比白名单、文件体积上限、黑名单标签（对应官方 tag_blacklist）
5. **校验**：下载完成校验 `Content-Length` + `sha256`，损坏自动重下

## 7. 风险登记册

| 风险 | 等级 | 应对 |
|---|---|---|
| API 无预警变更/字段缺失 | **高** | ACL + 全字段 optional + 契约测试 + 远程降级开关 |
| 45/min 限流导致体验卡顿 | 中 | 令牌桶 + 预取 2 页 + 本地缓存优先（先出 DB 再打网络） |
| 254 页上限 → 无法全量抓取 | 中 | 设计上承认"按需抓取"，用多维过滤切片扩大覆盖面 |
| 内存/大图 OOM（8K 原图） | **高** | Coil 按显示尺寸采样；原图仅在下载/预览全屏时加载 |
| 版权与合规 | 中 | 仅个人离线缓存；不做二次分发；保留 `uploader`/`source` 元数据；README 明示非官方 |
| 桌面 JRE 打包体积 | 低 | jpackage + 裁剪 module；或用 `jlink` 自定义运行时 |
| 单人开发周期失控 | 中 | 严格按 M0–M5 里程碑，M1 结束即出可运行 demo，不做提前抽象 |

## 8. 需你拍板的 5 个问题

1. **技术栈**：接受 Kotlin+CMP？（若不接受，请在 Rust/Tauri 与 Flutter 中指出偏好，我出对应细化方案）
2. **NSFW 策略**：默认不启用（仅 SFW），Key 由用户自填？还是完全不做该能力？
3. **"清洗数据"的终极目标**：只是本地整理？还是要导出 CSV/JSON 供外部使用（如喂给壁纸机器人、做数据集）？
4. **是否要"壁纸自动轮换"**：这是桌面端最有价值的差异功能，但涉及系统托盘常驻与开机自启，工作量大。
5. **发布范围**：仅自用 + 开源 GitHub？还是要上架 Google Play / 微软商店（涉及合规审核、隐私政策）？
