## 二、你的决策带来的新工作量与实测校正

### 2.1 ★ 第 2 条（瀑布流）—— 我已经实测跑通了

**好消息：瀑布流在 Slint 里可以实现，且已验证。**

我写了一个独立原型，用「二维模型 + 列布局」方案：

```slint
ScrollView {
    HorizontalLayout {
        for col in root.columns-data : VerticalLayout {   // 外层：每列
            spacing: 6px;
            width: 200px;
            for img in col : Image {                       // 内层：该列图片
                source: img;
                width: 200px;
                height: 130px;
                image-fit: cover;
            }
        }
    }
}
```

Rust 侧按 `i % NCOLS` 把图分到各列，高度按**原图宽高比**计算。

**实测日志（真实运行）：**
```
[masonry] got 24 items, 4 columns
[masonry] #0 kx33m1 -> col0 200x113    ← 16:9 横图
[masonry] #7 m3q1r1 -> col3 200x280    ← 竖图（2109x2954）
[masonry] #12 o59k2l -> col0 200x309   ← 更高的竖图
```

**不同高度的图片错落排列，视觉效果就是瀑布流。** 窗口正常运行，内存 148.6MB。

### 2.2 ⚠️ 但瀑布流暴露了一个新问题：列高不均

当前用 `i % NCOLS` 简单轮询分列，会导致**各列高度差很大**（有的列累计 1200px，有的只有 800px），滚动到底部时会看到空白。

**解决办法（我会实现）**：分列时按"当前最短列"优先放入，这是标准 waterfall 算法：

```
每次放图时，选择当前累计高度最小的那一列放入
```

这样各列高度基本齐平。**这个算法不复杂（约 20 行代码），我直接做掉。**

## 三、★ 实测新发现的 4 个问题（你未提及但必须决定）

### 问题 1：缩略图尺寸选择——`small` 反而不如 `large`

实测三种缩略图的**真实像素与体积**（以 7680×4320 的图为例）：

| 版本 | 实际尺寸 | 体积 | 评价 |
|---|---|---|---|
| `small` | **300×200** | 16.5 KB | 200px 列宽下勉强够，**高 DPI 屏会糊** |
| `large` | **432×243** | **15.1 KB** | ✅ **比 small 还小，但更清晰！** |
| `original` | 300×169 | 13.9 KB | 比例被压过，不推荐 |

**这是个反直觉的发现**：`large` 分辨率更高，但压缩率更好，体积反而比 `small` 小。

> ⚠️ 注意：`small` 的名义尺寸是 300×200，但实测拿到的 `kx33m1` 的 small 是 300×200（16:9 的图被塞进 3:2 框？）。需要在实际开发中用更多样本验证。但 `large` 更清晰且体积更小这点是确定的。

**建议**：瀑布流缩略图用 **`large`**。

**你同意吗？** → ☐ 用 large / ☐ 用 small（省内存）

### 问题 2：DPI 缩放下的图片清晰度

Windows 上 125%/150% 缩放很常见。若列宽 200px，在 150% DPI 下实际需要 300px 像素——`small`（300×200）刚好卡在边缘，`large`（432×243）有余量。

**建议**：按 `列宽 × DPI倍率` 计算需要的像素，再决定用哪档。我会在代码里自动处理。

### 问题 3：无限滚动的"下一页"触发时机

wallhaven 每页固定 24 条。瀑布流 4 列时，24 条 = 每列 6 张。

**问题**：用户滚到底部很快（24 张只够滚 2 屏），会频繁触发加载。

**建议**：预取阈值设为"剩余 2 行（约 8 张）时请求下一页"，同时保持最多 3 个请求在途。

**你接受吗？** → ☐ 接受

### 问题 4：★ 限流 45 次/分钟 与瀑布流的冲突

这是个**真实的架构矛盾**，必须提前解决：

- 瀑布流让用户滚得很快 → 想加载更多 → 每页 24 条就要 1 次 API 请求
- 但限流只有 **45 次/分钟**
- 如果用户快速滚动，**30 秒内就能耗尽 45 次配额**

**更严重的是**：如果还要给每张图请求详情（拿 tags），24 张图 = 24 次请求，一页就耗掉一半配额。

**我的解决方案（需要你确认）**：

| 策略 | 说明 |
|---|---|
| ① 列表页**不请求详情** | 只用列表 API 返回的字段（无 tags），标签在用户点开详情时才拉 |
| ② 严格令牌桶 | 45/min，超了排队，UI 显示"正在排队" |
| ③ 本地缓存优先 | 同一查询 10 分钟内不重复请求，直接用缓存 |
| ④ 限制预取深度 | 最多预取 3 页，再往后需要用户主动点击 |

**你认可这套策略吗？** → ☐ 认可 / ☐ 有调整
