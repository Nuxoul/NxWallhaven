> 所有结论均来自本次**实测**（PowerShell 直接打接口 / 读官方文档 / 查包管理器），非记忆。
> 实测时间：2026-10-19

## 一、目标站点能力核验（wallhaven.cc API v1）

### 1.1 端点清单（官方文档 `https://wallhaven.cc/help/api`）

| 端点 | 用途 | 需 API Key |
|---|---|---|
| `GET /api/v1/w/{id}` | 单图完整详情（含 tags、uploader） | NSFW 时需要 |
| `GET /api/v1/search` | 检索/列表 | NSFW 时需要 |
| `GET /api/v1/tag/{id}` | 标签信息 | 否 |
| `GET /api/v1/settings` | 当前用户浏览器设置 | **是** |
| `GET /api/v1/collections` | 自己的收藏夹（含私有） | **是** |
| `GET /api/v1/collections/{user}` | 他人公开收藏夹 | 否 |
| `GET /api/v1/collections/{user}/{id}` | 收藏夹内壁纸列表 | 私有需 Key |

### 1.2 检索参数（全部可用）

`q`（支持高级语法）、`categories`、`purity`、`sorting`、`order`、`topRange`、`atleast`、`resolutions`、`ratios`、`colors`、`page`、`seed`

其中 `q` 支持的高级语法实测覆盖：
- `+tag1 +tag2` 必须同时含
- `-tag` 排除
- `@username` 按上传者
- `id:123` 精确标签（不可与其他条件组合）
- `type:png` 按文件类型
- `like:{id}` 找相似图

> **产品含义**：网页端的检索能力可通过 API **100% 还原**，无需 DOM 抓取。

### 1.3 实测数据（本次真实请求）

```
GET /api/v1/search?q=cyberpunk&categories=111&purity=100&sorting=relevance&atleast=2560x1440
→ 24 items, per_page=24, total=2871, last_page=120
→ 首条: id=kx33m1, 7680x4320, image/jpeg, 1.32MB

GET /api/v1/search?sorting=toplist&topRange=1M
→ total=1951, per_page=24

GET /api/v1/w/kx33m1
→ 详情含 tags[0]="Cyberpunk: Edgerunners", uploader=zireael(Group:User)
```

**列表项字段**（实测枚举）：
`id, url, short_url, views, favorites, source, purity, category, dimension_x, dimension_y, resolution, ratio, file_size, file_type, created_at, colors, path, thumbs{large,original,small}`

**详情独有字段**：`uploader, tags[]`

### 1.4 深分页上限（重点发现）

| 请求 page | 返回 |
|---|---|
| 120 | 24 条，last_page=254 |
| 200 | 24 条 |
| 500 | **0 条**（未报错，返回空数组） |
| 1000 | 0 条 |

→ **单一查询最多翻 254 页 ≈ 6096 张**，超出后静默返回空。这对"抓全站"类需求是硬天花板，必须用多维过滤切片绕开。

### 1.5 限流与鉴权

- **45 请求/分钟**，超限返回 `429`
- 无 Key 访问 NSFW → `401`
- Key 传递方式：`?apikey=` 或 `X-API-Key:` header（推荐后者，避免 URL 泄漏进日志）
- 图片直链 `w.wallhaven.cc` **不占 API 配额、无需鉴权**，可独立并发下载

### 1.6 官方免责声明原文要点

> "This API is provided for free and as-is with no warranty." + "changes to be made without warning"

→ 客户端必须做**字段容错**（全 optional）与**版本降级开关**。

### 2.3 ★ Kotlin 桌面端可行性 —— 已实测跑通（不是推断）

为消除「Kotlin 只能写安卓」的疑虑，本次**真实建工程、真实编译、真实出窗口**：

| 验证项 | 结果 |
|---|---|
| Maven Central 桌面构件 | ✅ `org.jetbrains.compose.desktop:desktop-jvm`、`desktop-jvm-windows-x64`、`ui-desktop` 均有 **1.12.2** 稳定版 |
| Skiko 原生渲染库 | ✅ `skiko-awt-runtime-windows-x64` **0.153.0** 存在（本次实际拉取 0.150.2） |
| `gradle compileKotlin` | ✅ BUILD SUCCESSFUL（2m6s） |
| `gradle createDistributable` | ✅ 产出 `kt-desktop-proof.exe` |
| **原生窗口真实弹出** | ✅ 枚举到窗口标题 **WH Studio - Compose Desktop Proof** |
| 运行时原生依赖 | ✅ 包内含 `skiko-windows-x64.dll`（14.1MB，真 Skia 原生渲染，非 WebView） |

产物结构（实测）：

```text
build/compose/binaries/main/app/kt-desktop-proof/
  kt-desktop-proof.exe          535,552 B     <- 原生启动器
  app/                                        <- 全部 jar (含 material3-desktop / ui-desktop)
    skiko-windows-x64.dll       14,119,424 B  <- Skia 原生渲染引擎
  runtime/                                    <- 裁剪后的 JRE
```

**踩到的 3 个真实坑（已解决，写进方案避免重蹈）**：

1. Compose >= 1.6.10 **必须**单独应用 `org.jetbrains.kotlin.plugin.compose`，否则配置阶段直接失败。
2. `compose.material3` 的版本序列**独立**于 Compose 插件（实测 material3 稳定线为 **1.9.0**，插件为 1.12.2）；手写 `org.jetbrains.compose.material3:material3:1.12.2` 会 404，必须用 `compose.material3` 依赖访问器。
3. 不要同时应用 `application` 插件与 `org.jetbrains.compose` —— `run` 任务重名，报 `Cannot add task 'run' as a task with that name already exists`。

> 结论：「Kotlin 不支持桌面端」是误解。准确说法：**Kotlin/JVM + Compose Multiplatform 的桌面端是官方一等支持目标，能产出原生 .exe，渲染走 Skia 而非 WebView。**

## 三、逐项对比分析

### 3.1 Kotlin + Compose Multiplatform

**实测体积数据（诚实披露，这是该方案唯一实质短板）**：

| 组成 | 实测大小 |
|---|---|
| 裁剪后 JRE（runtime/） | **64.7 MB**（139 个文件） |
| app/ 内全部 jar + skiko DLL | 约 **49.7 MB**（其中 skiko-windows-x64.dll 14.1MB） |
| **分发包总计** | **114.4 MB** |

对比：Tauri v2 同类应用约 8–15MB。**差距约 8 倍**。
缓解手段：`jlink` 进一步裁模块（去 javafx、字体等）可压到 ~70MB；或用 `packageMsi` + LZMA 压缩安装包（约 40–50MB）。若你对安装包体积极其敏感，这是应该重新考虑 Tauri 的唯一理由。

**优势**
- Android 是 Kotlin 主场：`WallpaperManager`（设壁纸）、`WorkManager`（后台下载）、`MediaStore`、`Keystore` 全原生
- 一套 `@Composable` 同时编译到 Windows（Skiko 渲染）与 Android（Skia）
- Coil 3 是 KMP 原生项目，`AsyncImage` 两端通用，自带内存/磁盘/三级缓存
- SqlDelight 共享 SQL schema，两端各生成类型安全 DAO
- 领域层纯 Kotlin，单测覆盖率可做到 100%，无 JVM 之外负担

**劣势（必须承认）**
- 桌面端需要打包 JRE，安装包 ~80–100MB（可用 jlink 裁剪到 ~50MB）
- 壁纸设置/托盘/开机自启需少量 JNI 或第三方库（`com.github.kdroidfilter` 系列）
- 内存基线比 Rust 高（桌面空载 ~120MB vs Tauri ~40MB）

### 3.2 Rust + Tauri v2

**优势**
- 包体最小（~10MB）、内存最低
- Rust 侧原生调 Win32 API（`SystemParametersInfoW` 设壁纸）非常干净
- 前端可用 React/Svelte，写复杂列表也舒服

**劣势**
- 安卓端要求 Android Studio + NDK 环境变量 + Studio 自带的 JBR（本机全缺）
- WebView 渲染：Windows 用 WebView2（需系统组件），Android 用 System WebView（版本碎片化）
- 图片密集列表在 WebView 里做虚拟滚动，性能上限不如原生 LazyGrid
- **双份技术栈**（Rust + JS），单人维护成本高

### 3.3 Go（Wails / Fyne）

- **Wails**：官方无移动端；社区曾讨论，但至今未进主线 → 直接出局
- **Fyne**：跨平台一时爽，但图片网格滚动、手势、文本渲染质量是硬伤；Material 3 无法用
- Go 语言本身无问题，问题在 GUI 生态

> **Go 的合理归宿**：若将来要做一个**独立的 CLI 批量抓取/清洗工具**（无 UI），Go 是极佳选择。可与 GUI 项目并存。

### 3.4 Flutter

- 两端都成熟，UI 一致性强，图片性能好（`cached_network_image`）
- 问题：Dart 生态与现有 Kotlin/Gradle 割裂；桌面打包同样要带 runtime；团队若以 Kotlin 为主则无收益
- **如果开发者本身熟 Dart，这是仅次于 Kotlin 的选择**

### 3.5 C# / Avalonia 或 WinUI

- Windows 端最佳（WinRT 壁纸、托盘、MSIX 全原生）
- Android 需 .NET MAUI 或 Avalonia 的社区 Android 后端，成熟度不足
- 排除

## 四、必须提前想清楚的产品级难题

### 4.1 "拥有网页端的一切功能" 的真实边界

| 网页端功能 | API 能否还原 | 说明 |
|---|---|---|
| 搜索/筛选/排序 | ✅ 完全 | 参数一一对应 |
| 瀑布流浏览 | ✅ | 需自己做虚拟滚动 |
| 详情页/标签/相似推荐 | ✅ | `like:{id}` |
| 登录账号 | ⚠️ 部分 | API v1 **只支持 API Key**，没有 OAuth/密码登录流程 |
| 收藏/点赞（写操作） | ❌ **不支持** | API v1 是**只读**的，无法收藏/评分/上传 |
| 上传壁纸 | ❌ | 无写接口 |
| 论坛/评论 | ❌ | 无接口 |
| 用户主页 | ❌ | 无接口 |

> **这是本项目最大的预期管理点**：`"拥有网页端一切功能"` 在当前 API 下**做不到**。可做到"浏览 + 检索 + 下载 + 本地管理"的完整体验；写操作要么引导用户在浏览器完成，要么等官方开放 API v2。

### 4.2 254 页上限 → "清洗数据"要重新定义

既然无法"抓全站"，数据清洗应定位为：
- **按需抓取**：用户关注的标签/画师/颜色组合，各抓 N 页
- **持续增量**：定时任务拉 `sorting=date_added` 的前几页，入库去重
- **多维切片**：用 `atleast` × `ratios` × `categories` 排列组合，扩大单主题覆盖

### 4.3 大图内存风险

实测存在 7680×4320 图片。解码后单张 RGBA 约 **132MB**。必须：
- 列表只用 `thumbs/small`（~10KB）或 `large`
- 详情预览用 Coil 的 `size()` 限制到屏幕尺寸采样
- 原图仅"下载"和"全屏查看"时才解全尺寸

## 五、结论

1. **技术栈：Kotlin + Compose Multiplatform**（详见 `00-立项决议.md` 决策矩阵）
2. **Rust 留作 Phase 3 的加速模块**，不承担 UI
3. **Go 只用于将来可能的 CLI 工具**，不用于双端 GUI
4. **产品范围必须收缩**到"只读体验 + 本地数据管线"，写操作不可承诺
5. **数据抓取必须承认 254 页天花板**，采用切片 + 增量策略
