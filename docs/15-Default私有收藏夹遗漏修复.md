# Default 私有收藏夹遗漏

## 真实复现与根因

用户反馈“默认 Default 收藏夹为什么没有”。本轮先在实际运行的客户端复现：当前网站账号的“我的收藏夹”及管理窗口只有一个自建收藏夹，没有 Default。

随后在同一已登录 WebView2 会话，只读打开网站页面核对：

- `/user/<用户名>/favorites` 明确标为 Public Collections，并提示仅显示公开收藏，网站提供的 Manage Collections 链接指向 `/favorites`。
- `/favorites` 的自己的收藏侧栏显示 Default（4 张，Private）和自建收藏夹（9 张）。Default 使用真实的正整数 ID 和 `/favorites/<ID>` 地址，不是 `0` 号。
- 旧客户端虽然完成网站登录，却仍从公开资料页读取列表/内容，且解析器只认识公开条目地址，因此遗漏了私有 Default。

此前“收藏夹列表完整”的结论不成立；公开账号读取成功不能证明自己的私有列表完整。没有靠猜测 ID、伪造空 Default 条目或取消 ID 验证来掩盖问题。

## 修复

- 已验证网站账号的自己的列表读取 `/favorites`，严格核对请求账号与会话账号一致。
- 收藏内容及后续页读取 `/favorites/<真实ID>?page=...&purity=...`，不再用公开资料路径读取私有收藏。
- 内置网页管理打开真正的 `/favorites`；表单发现也从自己的收藏页起步。写入仍保留明确确认、不猜路由、不重试未知结果等限制，本轮不执行真实写入。
- 解析自己的 `.collections-list`/`#collections`，接受同源精确 `/favorites/正整数ID` 链接，排除 Trash、其他用户、外域、0 号和可疑查询链接。
- 兼容侧栏文字名称、小型数量元素、私有 `fa-eye-slash` 标记，不把图标/数量拼入名称。
- 自己的列表中工具链接位于内容链接之前；解析器现在寻找符合收藏内容路径的链接，不取首个改名/隐私/删除链接。条目自身 private/public 标记优先，不能把隐私切换按钮图标当作当前状态。
- 收藏列表分页仅跟随收藏侧栏/列表的分页，不能误跟随同页图片的分页。
- “公开收藏”仍走原公开 API，界面状态明确区分自己的/账号/公开列表。
- 内容 purity 继续使用应用筛选；网站账号默认可见范围不会自动开放 NSFW。
