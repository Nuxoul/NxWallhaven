## 二、实测踩到的 3 个坑（**必须写进架构决策**）

### 坑 1：`slint::Image` **不是 Send**，不能跨线程

这是最关键的发现。最初设计想让后台线程直接产出 `Image` 推进 model，编译直接失败：

```
error[E0277]: `Rc<VecModel<slint::Image>>` cannot be sent between threads safely
```

**正确架构（已验证）：**

```
后台线程（Send 域）
  ├─ reqwest 下载字节
  ├─ image 解码
  ├─ resize_exact 降采样
  └─ 产出 (w, h, Vec<u8>)  ← 纯字节，可跨线程
        │
        ▼ upgrade_in_event_loop
UI 线程（event loop）
  ├─ SharedPixelBuffer::<Rgba8Pixel>::new(w, h)
  ├─ copy_from_slice(&rgba)
  ├─ Image::from_rgba8(buf)     ← 只能在这里构造
  └─ model.set_row_data(idx, img)
```

### 坑 2：`VecModel` 不实现 `Clone`，`Rc<VecModel>` 也不是 `Send`

想用 `Rc<VecModel>` 跨线程持有会失败。**正确做法**：在 UI 线程的闭包内，从 UI 属性取回 model 句柄：

```rust
let _ = ui_weak.upgrade_in_event_loop(move |ui| {
    if let Some(vm) = ui.get_thumbs().as_any().downcast_ref::<VecModel<Image>>() {
        vm.set_row_data(idx, img);
    }
});
```

### 坑 3：`GridLayout` 用动态索引会 panic

把 `Math.mod(idx, columns)` / `Math.floor(idx / columns)` 塞进 `GridLayout` 做瀑布流，超出初始行数时运行时崩溃：

```
thread 'main' panicked at i-slint-core/layout.rs:567:
index out of bounds: the len is 8 but the index is 10
```

**结论**：Slint 的 `GridLayout` **不是懒加载/虚拟化的**，不能直接当 LazyGrid 用。
**替代方案**（本项目采用）：把数据在 Rust 侧按行切分，每行一个 `HorizontalLayout`，行放进 `ScrollView` 里的 `VerticalLayout`。

> 这也是 Slint 与 Compose 的关键差异：Compose 的 `LazyVerticalStaggeredGrid` 天生虚拟化，Slint 需要自己实现。

### 补充坑 4：Slint 语法细节

- 不支持 `%` 取模 → 用 `Math.mod(x, y)`
- 除法取整 → 用 `Math.floor(x / y)`

## 三、对方案 B 架构的影响

### 3.1 图片管线必须自己实现（原判断得到证实）

Coil 提供的这些能力，在 Slint 里全要自己写：

| 能力 | Coil (Kotlin) | 方案 B (Rust) |
|---|---|---|
| 网络下载 | ✅ 内建 | ✅ reqwest（已通） |
| 解码 | ✅ 内建 | ✅ image crate（已通） |
| 采样降档 | ✅ 自动 | ✅ resize_exact（已通） |
| 内存缓存 | ✅ LRU 自动 | ❌ **需自己写 LRU** |
| 磁盘缓存 | ✅ 自动 | ❌ **需自己写** |
| 滚动时暂停请求 | ✅ 自动 | ❌ **需自己写** |
| 层级虚拟化 | ✅ LazyGrid | ❌ **需自己写** |

**新增工作量估算：约 1.5–2 周**（LRU 缓存 + 虚拟滚动 + 请求调度）

### 3.2 内存表现良好

24 张 210×130 缩略图，总计：
- 每张 109,200 bytes（210×130×4 RGBA）
- 24 张 = 2.62 MB
- 进程总计 87.3 MB（含 Slint 渲染器 + rustls 等）

**结论：可安全支持数千张缩略图**，只要 LRU 限制在 200–500 张，内存增量约 20–50MB。
